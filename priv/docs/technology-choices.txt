# ali 技术方案与选型对比

> 本文档梳理 ali 项目当前的功能清单、各功能使用的技术方案、方案在项目中的
> 关联性、可替代方案对比，以及方案的详细介绍。作为架构演进和决策参考。
>
> 最后对照代码更新：2026-07-20（`src/core` 基础设施目录；`memory/` / `skill/` 独立；运行时加固）

## 1. 项目定位

ali 是嵌入 Erlang 节点的 **运行时感知 AI 开发助手**。核心能力：

- 对 Erlang 源码做 Tree-sitter AST 解析、BM25 + 可选向量混合检索、调用关系图遍历
- 对接 **OpenAI 兼容** LLM 协议（当前默认 DeepSeek 对话 API）实现 agent 问答、补丁生成与回滚
- 通过 **MCP / HTTP / WebSocket / Erlang API / 终端 REPL** 对外服务
- 运行时探针：进程、ETS、supervisor 树、白名单 MFA
- Web UI：浏览器内对话、计划、审批、会话管理

设计目标：

1. **单机零外部依赖即可运行**：SQLite bundled、本地 `embeddings.json` fallback、无 Qdrant 时 BM25 仍可用
2. **可选渐进升级**：Embedding API → Rerank → Qdrant 托管或外接
3. **进程隔离**：重型计算在 Rust `aliCore` 子进程，crash 不拖垮 BEAM

### 2.1 监督树启动顺序（`ali_sup`）

| 顺序 | 子进程 | 说明 |
|------|--------|------|
| 1 | `aliQdrant` | 可选托管 `priv/qdrant`（Port），或仅连接外部 URL |
| 2 | `aliLocalDb` | Erlang 侧 DB 门面，Rust Core 不可用时 JSONL 回退 |
| 3 | `aliSessionMgr` | 会话持久化 |
| 4 | `aliCoreClient` | 拉起 `aliCore --port`，请求队列化 |
| 5 | `aliCodeIndex` | Erlang MVP 索引（Core 不可用时的回退） |
| 6 | `aliServer` | 会话路由与 ask 入口 |
| 7 | `aliWebSup` | **最后启动**：HTTP/WS 依赖 session_mgr + aliServer |

Web 监听失败（如 `eaddrinuse`）时 **不崩溃** `ali_sup`，仅将网关标记为 `enabled => false`，核心 Agent 仍可运行。

### 2.2 职责边界

| 层 | 职责 | 不负责 |
|----|------|--------|
| **Erlang Web** | eWSrv HTTP/WS、静态资源、REST/SSE、鉴权限流 | 索引、AST、向量 |
| **Erlang Agent** | 会话、tool loop、策略审批、补丁安全、上下文组装 | 重型检索 |
| **Erlang 工具** | `aliToolCatalog` 统一注册 ~47 个内置工具 | Tree-sitter 解析 |
| **Rust aliCore** | 索引/检索/调用图/SQLite/记忆向量 | 直接操作 BEAM |

## 4. 各方案选择与对比分析

### 4.1 进程间通信：Erlang Port（{packet,4} JSON）

**当前方案**：Erlang 用 `erlang:open_port({spawn, "aliCore --port"}, [{packet,4}])`
拉起 Rust 子进程，双方通过 stdin/stdout 交换 4 字节大端长度前缀 + JSON body
的二进制消息。请求队列化，并发调用者不会收到 `{error, busy}`。

**在项目中的关联性**：
- `alCoreClient` (gen_server) 是唯一的 Port 持有者，所有 Rust 调用经此排队
- Rust Core 仅支持 `--port` 模式（HTTP 模式已移除，Web 由 Erlang eWSrv 提供）
- 工具路由器 `alToolRouter` 优先走 `alCoreClient`，失败回退 Erlang 实现

**选型理由**：
- **进程隔离**：Rust crash 不会拖垮 BEAM，Erlang supervisor 可自动重连
- **无 GC 压力**：重型计算（AST 解析、向量检索）在 Rust 堆上完成
- **调试友好**：Rust 可独立以 `--port` 模式运行，手动发 JSON 测试
- **协议简单**：JSON 可读，{packet,4} 自带长度分帧

**对比方案**：

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|---------|
| **Port（当前）** | 进程隔离、crash 安全、可独立调试 | JSON 序列化开销、单进程串行 | 重型计算、需要隔离 |
| NIF (Rustler) | 零拷贝、极低延迟 | crash 拖垮 BEAM、需 dirty scheduler | 轻量计算、低延迟 |
| HTTP (axum→Erlang) | 标准协议、可远程部署 | 启动需绑端口、网络栈开销 | 多节点共享 core |
| Unix Socket | 比 HTTP 轻量 | Windows 兼容差 | 单机高频调用 |

**方案详细介绍**：
Erlang Port 是 OTP 内建的与外部程序通信机制。`open_port({spawn, Cmd}, Opts)`
启动外部进程，通过管道收发二进制。`{packet, 4}` 选项让 Erlang 自动处理 4 字节
大端长度前缀的打包/拆包——发送时自动加前缀，接收时按前缀截取完整消息。
这避免了手写流式分帧逻辑。JSON 作为 payload 格式，用 `alJson` (jiffy)
编解码，跨语言无歧义。`alCoreClient` gen_server 维护请求队列：inflight
一个请求时其余排队，port 关闭时 drain 队列并回复错误，自动调度重连。

**结论**：Port 是重计算场景的最佳折中。若未来需要 NIF 级延迟（如逐符号补全），
可对特定纯函数用 Rustler 做 NIF，保留 Port 处理索引/检索。

### 4.2 HTTP 服务器：eWSrv

**当前方案**：[alHttpGateway.erl](../src/src/web/alHttpGateway.erl)
用 eWSrv 库监听端口，`alWebHandler` 作为 eWSrv 回调模块处理 HTTP 请求和
WebSocket 升级。Web UI 和工具 API 共用同一端口。

**在项目中的关联性**：
- `alWebHandler` 实现 eWSrv 的 `init/1`、`handle/3`、`handleWs/3`、`terminate/2`
- HTTP 路由分发到 ~33 个端点（REST API + 静态资源 + MCP 兼容）
- WebSocket 升级后委托 `alWs:dispatch/3` 处理命令
- `alWebConnSup` 管理连接进程，`alWebSup` 管理整个 Web 子树

**选型理由**：
- **轻量**：比 Cowboy 小，满足 HTTP + WS 双需求
- **OTP 原生**：用 supervisor 管理连接，进程模型清晰
- **chunked 支持**：`{chunkedSupp, true}` 支持 SSE 流式输出
- **WS 内建**：无需额外 WebSocket 库

**对比方案**：

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|---------|
| **eWSrv（当前）** | 轻量、HTTP+WS 一体 | 私有库、文档少 | 嵌入式 Web |
| Cowboy | 成熟、生态丰富、HTTP/2 | 依赖较重 | 对外 Web 服务 |
| Bandit (Elixir) | 现代、Plug 生态 | 需 Elixir | Elixir 项目 |
| elli | 轻量 Erlang HTTP | 维护不活跃、无 WS | 轻量 HTTP |
| 手写 gen_tcp | 零依赖 | 需自己处理 HTTP 边角 | 内网极简 API |

**方案详细介绍**：
eWSrv 是一个 Erlang 实现的 HTTP/WebSocket 服务器库。它通过 `wsMod` 参数指定
回调模块，每个连接是一个 gen_server 进程。回调模块实现 `handle/3` 处理 HTTP
请求，`handleWs/3` 处理 WebSocket 帧。`wsSupName` 指定连接 supervisor，
`chunkedSupp` 启用 chunked transfer encoding 支持（SSE 流式必需）。
`alHttpGateway` 处理 `eaddrinuse` 时自动重试一次。

**结论**：eWSrv 满足当前需求。若未来需要 HTTP/2 或更丰富中间件，可迁移到 Cowboy。

### 4.3 JSON 处理：jiffy via alJson

**当前方案**：[alJson.erl](../src/src/llm/alJson.erl) 作为 jiffy
的边界封装，提供 `encode/1`、`decode/1`，处理 UTF-8 修复、sanitize、三档编码。

**在项目中的关联性**：
- 所有 JSON 编解码统一走 `alJson:encode/1` 和 `alJson:decode/1`
- Port 通信的 payload 用 alJson 编解码
- LLM 响应解析、WebSocket 消息、配置加载均依赖此模块
- `decode/1` 使用 `[return_maps]` 选项，返回 map 而非 proplists

**选型理由**：
- **性能**：jiffy 是 C NIF，比纯 Erlang 的 json 模块快 5-10 倍
- **边界封装**：统一处理 UTF-8 修复、sanitize，避免各处重复
- **map 友好**：return_maps 选项与现代 Erlang 代码风格一致

**对比方案**：

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|---------|
| **jiffy via alJson（当前）** | 高性能、边界封装 | C NIF (crash 风险) | 高频 JSON |
| json (OTP 内建) | 纯 Erlang、零依赖 | 慢 5-10 倍 | 低频 JSON |
| thoas | 纯 Erlang、快 | 无边界封装 | 纯 Erlang 项目 |
| jsone | 功能全 | 慢于 jiffy | 需要 feature |

**结论**：jiffy + alJson 边界封装是性能和安全性的最佳平衡。

### 4.4 HTTP 客户端：hackney

**当前方案**：[alLlmClient.erl](../src/src/llm/alLlmClient.erl)
用 hackney 发送 LLM API 请求，支持流式 (stream) 和非流式两种模式。

**在项目中的关联性**：
- LLM 聊天、流式输出、embedding API 均通过 hackney
- `do_chat_with_retry/5` 有 429/5xx 指数退避重试
- `do_run_stream/4` 用 hackney streaming 接收 SSE
- 非 LLM 场景（MCP HTTP transport 如有）也用 hackney

**选型理由**：
- **成熟**：Erlang 生态最流行的 HTTP 客户端
- **连接池**：内建 pool 管理，复用 TCP 连接
- **流式**：原生支持 streaming response（SSE 必需）
- **SSL**：支持 hackney_ssl，比 inets 的 ssl 更稳定

**对比方案**：

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|---------|
| **hackney（当前）** | 成熟、连接池、流式 | 依赖 | 通用 HTTP |
| httpc (OTP 内建) | 零依赖 | 无连接池、流式弱 | 简单请求 |
| gun | 流式强、HTTP/2 | 维护不活跃 | HTTP/2 长连接 |
| ibrowse | 老牌 | 维护停滞 | 历史项目 |

**方案详细介绍**：
hackney 是 Erlang 的 HTTP 客户端库，支持连接池、流式响应、SSL、multipart 等。
它通过 `hackney:request/5` 发送请求，`hackney:body/1` 读取响应体。
流式模式用 `hackney:start_response` + `hackney:stream` 逐块读取。
`alLlmClient` 中 `do_chat_with_retry` 对 429 (rate limit) 和 5xx
做指数退避重试，最多 3 次；`do_run_stream` 对 SSE 流逐行解析 `data:` 前缀。

**结论**：hackney 是 LLM 流式调用的最佳选择。

### 4.5 MCP：JSON-RPC over stdio

**当前方案**：[alMcp.erl](../src/src/mcp/alMcp.erl) 实现 MCP
2024-11-05 协议，通过 stdio 收发 Content-Length 分帧的 JSON-RPC 消息，
暴露 tools/resources/prompts 三类能力。

**在项目中的关联性**：
- IDE（Cursor / Claude Desktop）通过 `mcp` 命令拉起 stdio server
- `alMcp:stdio/0` 入口：启动 ali 应用 → 初始化 Rust Core → mcp_loop
- 工具调用复用 `alToolCatalog:invoke/2`，与 HTTP/WS/Erlang API 同源
- `alMcpClient` 反向连接外部 MCP server，注册远程工具到 catalog

**选型理由**：
- **IDE 原生支持**：Cursor / Claude Desktop 等通过 `mcp` 命令拉起 stdio server
- **无端口占用**：stdio 传输，不额外监听端口
- **与 Port 模式互补**：MCP 用于 IDE，HTTP/WS 用于浏览器/curl，Erlang API 用于节点内

**对比方案**：

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|---------|
| **stdio JSON-RPC（当前）** | IDE 原生、无端口 | 单进程、不便并发调试 | IDE 集成 |
| HTTP SSE | 可流式、可并发 | 需端口、IDE 支持不一 | Web 客户端 |
| WebSocket | 双向、低延迟 | 实现重、需端口 | 实时双向 |

**方案详细介绍**：
MCP (Model Context Protocol) 是 Anthropic 提出的标准协议，让 AI 客户端
（IDE）与工具服务器通信。协议基于 JSON-RPC 2.0，传输层用 stdio +
Content-Length 分帧（每条消息前加 `Content-Length: N\r\n\r\n`）。
server 暴露三类能力：`tools`（可调用的函数）、`resources`（可读取的数据源）、
`prompts`（可触发的模板提示）。`alMcp` 实现 `initialize`、`tools/list`、
`tools/call`、`resources/list`、`resources/read`、`prompts/list`、
`prompts/get` 等方法。

**结论**：stdio 是 MCP 标准传输，保持现状。

### 4.6 全文检索：Tantivy BM25

**当前方案**：Rust 用 Tantivy 构建 BM25 倒排索引（`field`/`module`/`body`
三字段），支持 `module:`/`function:`/`arity:` 过滤，增量索引按 `file_hash`
跳过未变文件。

**在项目中的关联性**：
- `alCoreClient:search/2,3` → Rust Core `/search` 端点
- `alContextEngine:fetch_code_hits` 优先走 Rust，回退 `alCodeIndex`
- 索引落盘到 `priv/index/`，启动时自动加载
- `alCoreClient:index/1` 触发全量重建，`index_status/0` 查询状态

**选型理由**：
- **嵌入式**：单库依赖，索引落盘，无需起独立服务
- **Rust 原生**：与 Rust Core 同进程，零网络开销
- **BM25 成熟**：对代码这种 token 密集场景，BM25 优于纯 TF-IDF

**对比方案**：

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|---------|
| **Tantivy（当前）** | 嵌入式、Rust 原生、BM25 | 单机、无分布式 | 单机代码搜索 |
| MeiliSearch | 嵌入式、typo 容错 | 需独立进程、内存大 | 面向用户搜索 |
| PostgreSQL FTS | 复用现有 PG | 需 PG、BM25 弱 | 已有 PG |
| Elasticsearch | 分布式、强大 | 重型、JVM | 企业级全文 |

**方案详细介绍**：
Tantivy 是 Rust 实现的全文检索引擎，灵感来自 Lucene 但纯 Rust 无 JVM。
它支持 BM25 评分、倒排索引、字段加权、范围查询、facet 等。索引可持久化
到磁盘，启动时 mmap 映射，查询延迟在毫秒级。增量索引用 `file_hash` 判断
文件是否变更，跳过未变文件，大幅减少重建时间。

**结论**：Tantivy 是单机嵌入式场景的最佳选择。

### 4.7 向量检索：Qdrant 独立 collection + 本地 fallback

**关联性**：
- 环境变量由 `alConfig:core_port_env/0` 注入（`ALI_ROOT`、`ALI_INDEX_DIR`、`ALI_QDRANT_URL`、`ALI_INDEX_EXTENSIONS` 等）
- Rust **仅** `--port` 模式；曾有的 axum HTTP 已移除，对外 Web 全部由 Erlang eWSrv 提供
- `aliToolRouter` / `aliContextEngine` 优先 `aliCoreClient`，失败回退 `aliCodeIndex` 或空结果

**在项目中的关联性**：
- `alCoreClient:memory_search/2` → Rust `/memory/search`
- `alCoreClient:search_unified/2` → Rust `/search/unified`（BM25 + 向量混合）
- `alQdrant` gen_server 托管 Qdrant 子进程（可选）
- 无 Qdrant 时自动降级为本地 EmbeddingStore + 余弦相似度

**选型理由**：
- **渐进迁移**：无 Qdrant 时项目完全可用，有 Qdrant 时自动升级
- **物理隔离**：memory 和 code 用独立 collection，避免 payload schema 混乱
- **Qdrant 优势**：HNSW 索引、payload 过滤、REST/gRPC 双协议

**对比方案**：

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|---------|
| **Qdrant + fallback（当前）** | 渐进迁移、物理隔离 | 需额外部署 Qdrant | 生产向量检索 |
| 纯本地 HashMap | 零依赖 | 无 ANN 索引、规模受限 | 原型/小规模 |
| Milvus | 分布式、大规模 | 重型、需 etcd/minio | 亿级向量 |
| Weaviate | 自带 GraphQL | 内存占用大 | 多模态 |
| pgvector | 复用 PG | 无 HNSW、性能一般 | 已有 PG |

**memory 与 code 分 collection vs 同 collection + kind 过滤**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **Port（当前）** | 进程隔离、可独立调试、协议简单 | JSON 序列化开销、单 Port 串行 |
| NIF (Rustler) | 极低延迟 | crash 拖垮 BEAM |
| HTTP 远程 Core | 可共享、可扩展 | 需绑端口、运维复杂 |

**结论**：索引/检索/DB 等重计算保持 Port；若未来有高频纯函数需求，可对单点加 Rustler NIF，不替换整体架构。

### 4.8 AST 解析：Tree-sitter

**当前方案**：Rust 用 `tree-sitter` + `tree-sitter-erlang` 解析 `.erl` 文件，
通过 Query (S-expression) 提取函数/导出/spec/callback/record/macro/调用关系。

**在项目中的关联性**：
- 索引构建时解析所有 `.erl`/`.hrl` 文件
- 提取的符号存入 Tantivy (全文) 和 Qdrant (向量)
- 调用关系存入 petgraph DiGraph
- `alCoreClient:get_symbol/3`、`module_symbols/1` 查询符号
- `alCoreClient:get_callers/3`、`get_callees/3` 查询调用图

**选型理由**：
- **增量解析**：tree-sitter 原生支持增量，适配文件变更
- **跨语言一致**：未来加 Python/JS 支持只需换 grammar
- **Query 语法**：用 S-expression 声明式提取，无需手写遍历
- **错误恢复**：语法错误仍能提取已解析部分

| Rust 模块 | 职责 |
|-----------|------|
| `port.rs` | Port 帧读写、method+path 路由 |
| `main.rs` | 应用状态、索引、搜索、调用图、记忆、tree-sitter 解析 |
| `ignore.rs` | `.gitignore` + 默认忽略 + `ALI_INDEX_EXTENSIONS` 白名单 |
| `embedding.rs` | 远程 embedding + 本地 `embeddings.json` |
| `rerank.rs` | 可选 rerank |
| `qdrant_store.rs` | 代码 chunk 与记忆两个 collection |
| `db.rs` | SQLite 读写（read/write 模式校验） |

**索引流水线**：WalkDir → 忽略规则 → 按后缀解析（erl/hrl/文本）→ `state.json` 持久化 → Tantivy 重建（有变更时）→ 可选 embed → 可选 Qdrant upsert。

### 4.9 全文检索：Tantivy BM25

**当前方案**：字段 `file`、`module`、`body`（`searchable_body` 拼接符号名与正文）。支持 `module`/`function`/`arity` 过滤。无 embedding 配置时默认 `mode=bm25`。

**在项目中的关联性**：

- `alCoreClient:get_callers/3`、`get_callees/3` → 双向查询
- Agent 的 `find_callers`/`find_callees` 工具直接调用
- 用于重构时理解调用关系、查找瓶颈

**对比**：Tantivy（嵌入式） vs MeiliSearch / Elasticsearch —— 单机嵌入式场景选 Tantivy。

### 4.10 向量检索：Qdrant + 本地 fallback

**当前方案**：Rust 用 `rusqlite`（bundled 模式，自带 SQLite C 源码编译），
单文件 `priv/db/ali.db`，存储长期记忆（alMemory 表）和会话消息
（session_messages 表）。Core 不可用时 Erlang 侧 fallback 到
`priv/db/store/*.jsonl`。

**在项目中的关联性**：
- `alMemory` → Rust `/memory/upsert`、`/memory/search` → SQLite
- `alSessionMgr` → Rust DB 读写会话消息
- `alAudit` → 可选持久化到 SQLite
- `alLocalDb` 门面：Rust SQLite 优先，文件回退

**Qdrant 托管**（`aliQdrant`）：
- `{qdrant, #{enabled => true}}` 且未设 `qdrantUrl` 时，Port 拉起 `priv/qdrant`
- `httpPort` 默认 6333，`grpcPort` 6334；存储 `priv/qdrant/storage`
- 应用关闭时终止 Qdrant 子进程

**DeepSeek 场景**：`aliCfg.cfg` 中 `embedding.baseUrl => undefined` 时 **不调用** embedding API，检索退化为纯 BM25；要启用向量需另配 OpenAI 兼容 embedding 服务。

### 4.11 配置方案：alConfig + alKvsToBeam 动态编译

**当前方案**：`config/aliCfg.cfg` 是唯一配置源（Erlang term 列表）。
`alConfig:load/0` 读取后经 `alKvsToBeam` 动态编译为 `aliCfg` 模块，各模块
通过 `alConfig:get/1` 或 `aliCfg:getV/1` 读取。`config/sys.config` 仅为 rebar shell/release 占位（空列表），不承载业务配置。

**在项目中的关联性**：
- 所有模块通过 `alConfig:get/1` (带默认值) 或 `alConfig:get/2` 读取配置
- `alConfig:core_port_env/0` 将 cfg 中的 core/embedding/rerank/qdrant 配置
  注入为环境变量给 Rust Port 子进程
- Web 配置通过 `flatten_web_keys/1` 自动从嵌套 `web` map 生成扁平键
  （`web_rate_limit` 等），支持 runtime override
- `alWebSec:web_opt/2` 先查扁平键（runtime override），后回退到嵌套 map

**选型理由**：
- **热加载**：改配置后 `alConfig:load/0` 重新编译模块，无需重启
- **类型安全**：Erlang term 原生支持 atom/list/map，无需解析
- **单文件**：所有配置集中在一个 `.cfg` 文件

**对比方案**：

- `.erl`：函数、export、spec、callback、record、macro、调用边
- `.hrl`：record/macro 等，无函数 chunk
- 其它配置后缀：不走 grammar，按固定行数文本 chunk

**对比**：Tree-sitter（增量、错误恢复、可扩展 grammar）vs `syntax_tools`（仅 Erlang、无增量）—— 多后缀与跨语言扩展选 Tree-sitter。

### 4.13 Agent 工具循环：自建 tool loop

**当前方案**：`alAgent:run/2` 实现工具循环——调用 LLM → 若返回 tool_calls
→ 执行工具 → 将结果加入对话 → 再次调用 LLM，最多 30 步。

**在项目中的关联性**：
- `alSessionWorker:do_ask_1/5` spawn_monitor 调 `alAgent:run/2`
- `alToolRouter:run_with_tools/2` 处理 tool_calls 分发
- `alCritic:review/2` 对草稿答案做安全性审查
- `alMemory:distill/1` 从对话中提取长期记忆

**选型理由**：
- **可控**：每步可插入 audit、metrics、progress 事件
- **策略感知**：工具执行前检查 policy，需审批时挂起
- **缓存**：读工具结果可缓存（alToolCache）
- **进度**：每步 emit progress 事件，前端可实时展示

### 4.14 HTTP 服务器：eWSrv

**当前行为**：
- `aliWebHandler` 为唯一 HTTP/WS 回调模块
- Web UI 与 Gateway API **共用单端口**（`web.port` 优先）
- `openHttpPort/1`：`eaddrinuse` 时 sleep 200ms 重试一次；仍失败则 `enabled => false`，**不崩溃** 顶层 supervisor
- 打开监听前确保 `aliWebConnSup` 已 `start_link` 注册

**对比**：eWSrv（轻量 HTTP+WS）vs Cowboy（HTTP/2、生态）—— 当前嵌入式 Web 够用；需 HTTP/2 再评估迁移。

### 4.15 策略与审批：四级风险分级

**当前方案**：[alPolicy.erl](../src/src/agent/alPolicy.erl)
将工具分为四级：`read`（只读）、`execute_safe`（安全执行如 eunit）、
`execute_risky`（风险执行如 run_mfa）、`write`（写操作如 apply_patch）。
三种模式（ask/edit/exec）对应不同权限矩阵。需审批的工具调用挂起到
`alPending`，前端 approve/dismiss 后恢复。

**在项目中的关联性**：
- `alToolRouter:call_tool/3` 若 `enforce_policy=true`，调用
  `alPolicy:check_tool/3`
- 返回 `confirmation_required` 时，任务挂起到 `alPending`
- `alServer:approve/1`、`dismiss/1` 恢复或取消挂起任务
- WebSocket 推送 `confirmationRequired` 事件给前端
- `alPolicy:sanitize_term/1` 对 api_key/token 等敏感字段脱敏

统一 `encode/1`、`decode/1`（`return_maps`），Port payload、LLM 响应、WS 消息均经此模块。对比纯 Erlang `json`：jiffy C NIF 更快，由 `aliJson` 做边界封装。

### 4.16 HTTP 客户端：hackney

`aliLlmClient`：非流式/流式 chat、429/5xx 指数退避（`maxRetries` 默认 3）、SSE 逐行解析。DeepSeek 等国产模型通过改 `llm.baseUrl` + `llm.model` 接入，无需改协议代码。

### 4.17 补丁管理：validate → backup → apply → rollback

**当前方案**：[alPatchManager.erl](../src/src/agent/alPatchManager.erl)
实现安全补丁生命周期。Patch 格式 `#{file, replace => #{old, new}}`。
apply 流程：normalize → validate → 读原文件 → backup → replace_once → 写入。
事务记录在 ETS `ali_patch_transactions`，支持 rollback_last。

**在项目中的关联性**：
- `apply_patch` 工具调用 `alPatchManager:apply/1`
- `alBackup:backup_file/2` 在 apply 前备份原文件到 `.ali/backups/<ts>/`
- `rollback_patch` 工具调用 `alPatchManager:rollback_last/0`
- `dry_run_patch` 工具调用 `alPatchManager:dry_run/1`（不写文件）
- `alPolicy` 将 apply_patch 归类为 `write`，默认需审批

### 4.18 LLM 与 Agent：自建 OpenAI 兼容 + tool loop

**流程**：`aliSessionWorker` → `aliAgent:run/2` → `aliLlmClient:chat/4` → 若有 `tool_calls` → `aliToolRouter:call_tool/3`（经 `aliPolicy`）→ 结果回填 → 循环至 `maxSteps`。

**策略**：`ask`/`edit`/`exec` 三模式 × 四级工具风险；`confirmation_required` 挂起 `aliPending`，Web 推送审批。

**对比**：自建 vs LangChain/LangGraph —— 嵌入式、可审计、OTP 友好；复杂 DAG 工作流未来可引入显式状态机。

### 4.19 补丁管理：validate → backup → apply → rollback

**当前方案**：
- `alServer` 持有 `sessions=#{Sid=>Pid}`，每个会话一个 `alSessionWorker`

### 4.21 技能系统：内置 + Markdown

**当前方案**：[alSkill.erl](../src/src/skill/alSkill.erl)

**结论**：Markdown + YAML 是技能模板的最佳形式。

### 4.22 运行时探针：进程/ETS/Supervisor 采集

**当前方案**：[alRuntimeProbe.erl](../src/src/agent/alRuntimeProbe.erl)
采集 Erlang 节点运行时数据：进程列表（top N by memory）、ETS 表（top N）、

**在项目中的关联性**：

`config/aliCfg.cfg` 为唯一业务配置源；`alConfig:load/0` 动态编译 `aliCfg` beam，支持 `alConfig:patch/1` 热更新。`config/sys.config` 不承载业务项。

## 6. 方案选择原则总结

1. **零外部部署优先**：SQLite bundled、本地 EmbeddingStore fallback——
   无 Qdrant/无 LLM API key 时项目仍可运行
2. **渐进升级**：BM25 → +向量 → +rerank → +Qdrant，每层可选开关
3. **进程隔离**：Rust Port 隔离重型计算，crash 不影响 BEAM
4. **协议统一**：MCP / HTTP / WS / Erlang API 四入口共用
   `alToolCatalog`，一套注册表
5. **物理隔离**：memory 和 code 向量分 Qdrant collection，schema 解耦
6. **安全优先**：四级策略分级 + 审批 + 审计 + 补丁备份回滚
7. **边界封装**：alJson (jiffy)、alLocalDb (SQLite/JSONL) 统一边界，
   便于替换底层
